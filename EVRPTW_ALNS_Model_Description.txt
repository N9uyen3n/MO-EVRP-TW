# Scientific Report: A Multi-Objective Adaptive Large Neighborhood Search for the Electric Vehicle Routing Problem with Time Windows (EVRPTW)

## Abstract

This document provides a detailed description of a sophisticated solver for the Electric Vehicle Routing Problem with Time Windows (EVRPTW). The problem is modeled as a multi-objective optimization task with a hierarchical objective function designed to primarily minimize the number of vehicles, secondarily minimize total travel distance, and finally improve solution quality by balancing workload and minimizing the maximum route time. The implemented solution is based on the Adaptive Large Neighborhood Search (ALNS) metaheuristic, enhanced with a sophisticated Pareto archive, a Simulated Annealing-based acceptance criterion, and a powerful, multi-phase local search module for intensification. The framework also includes advanced features like Hypervolume-based convergence tracking and an optional Scatter Search phase for deep exploration.

---

## 1. Problem Definition

The Electric Vehicle Routing Problem with Time Windows (EVRPTW) is an extension of the classical Vehicle Routing Problem (VRP). It involves designing a set of optimal routes for a fleet of electric vehicles (EVs) to serve a group of customers, subject to various real-world constraints.

- A central depot serves as the starting and ending point for all vehicle routes.
- Each customer has a specific demand and a time window within which service must begin.
- The electric vehicles have a limited carrying capacity and a finite battery range.
- A set of charging stations are available, which can be visited by vehicles to recharge their batteries. These stations also have their own operational time windows.

The primary goal is to find a feasible set of routes that serves all customers while respecting all constraints and optimizing the given objectives.

### 1.1. Objectives

The problem is treated as a **hierarchical multi-objective optimization problem**. The objectives are prioritized as follows:

1.  **Primary Objective:** Minimize the total number of vehicles used. `(Minimize |K|)`
2.  **Secondary Objective:** Minimize the total travel distance of all routes. `(Minimize Σ TotalDistance_k)`
3.  **Tertiary Objective (1):** Minimize the workload imbalance between routes, measured by the Gini Coefficient of active route times. A lower Gini coefficient (closer to 0) indicates a more balanced workload. `(Minimize Gini(ActiveTime_k))`
4.  **Tertiary Objective (2):** Minimize the completion time of the longest route (makespan). `(Minimize Max(TotalTime_k))`

A solution A is considered to dominate solution B if it is better in at least one objective without being worse in any other, following the strict hierarchical order. For example, a solution with fewer vehicles is always better, regardless of other objective values.

## 2. Mathematical Formulation

*(This section remains unchanged as the mathematical model is standard. The novelty lies in the solution methodology.)*

### 2.1. Sets and Indices
- `D = {0}`: The set containing the central depot.
- `C = {1, ..., N}`: The set of customers.
- `S = {N+1, ..., N+M}`: The set of charging stations.
- `V = D ∪ C ∪ S`: The set of all nodes.
- `V' = C ∪ S`: The set of all possible visit locations.
- `K`: The set of available homogeneous electric vehicles.

### 2.2. Parameters
- `d_ij`: Distance between node `i` and node `j`.
- `t_ij`: Travel time between node `i` and node `j`.
- `q_i`: Demand of customer `i`.
- `[e_i, l_i]`: Time window for node `i`.
- `s_i`: Service time required at customer `i`.
- `C_k`: Maximum cargo capacity of vehicle `k`.
- `Q_k`: Maximum battery capacity of vehicle `k`.
- `h`: Energy consumption rate.
- `g_j`: Charging rate at station `j`.

### 2.3. Decision Variables
- `x_ijk`: Binary, 1 if vehicle `k` travels from `i` to `j`.
- `A_ik`: Arrival time of vehicle `k` at node `i`.
- `L_ik`: Remaining cargo load of vehicle `k` at node `i`.
- `B_ik`: Remaining battery level of vehicle `k` at node `i`.
- `c_jk`: Amount of energy charged to vehicle `k` at station `j`.
- `u_k`: Binary, 1 if vehicle `k` is used.

### 2.4. Objective Function
Minimize `(Z_1, Z_2, Z_3, Z_4)` where:
`Z_1 = Σ_{k ∈ K} u_k`
`Z_2 = Σ_{i,j,k} d_ij * x_ijk`
`Z_3 = GiniCoefficient({ActiveTime_k | k ∈ K, u_k=1})`
`Z_4 = Max_{k ∈ K} (CompletionTime_k)`

### 2.5. Constraints
*(Standard VRP, TW, Capacity, and Energy constraints apply.)*

## 3. Solution Methodology: Adaptive Large Neighborhood Search (ALNS)

The problem is solved using a sophisticated ALNS metaheuristic tailored for hierarchical multi-objective optimization.

### 3.1. Overall Framework

The ALNS algorithm starts with an initial solution and iteratively tries to improve it. In each iteration, a portion of the current solution is "destroyed" and then "repaired". The choice of destroy and repair methods is guided by an adaptive weight adjustment mechanism that rewards operators for finding high-quality solutions.

**Pseudo-code for ALNS Main Loop:**

```
Algorithm ALNSSolver.solve():
  Input: Instance, ALNSConfig config
  Output: ParetoArchive (set of non-dominated solutions)

  s_current = generateInitialSolution()
  archive.tryAdd(s_current)
  currentTemperature = config.startTemperature
  iterationsWithoutImprovement = 0
  perturbationBoost = 1.0
  
  // HV-based convergence state
  previousHV = 0.0
  hvStagnationCount = 0
  lastMinVehicles = s_current.getTotalVehicles()

  For iteration = 1 to config.maxIterations:
    s_new = s_current.copy() // Uses SolutionPool for efficiency

    // 1. Destroy Phase
    n_to_remove = calculateNodesToRemove(perturbationBoost)
    destroy_op = destroyPool.select(rng)
    unserved_custs = destroy_op.execute(s_new, n_to_remove, rng)
    
    // 2. Repair Phase
    repair_op = repairPool.select(rng)
    repair_op.execute(s_new, unserved_custs, rng)
    
    s_new.evaluateRoutes() // Re-evaluate feasibility and all objectives

    If s_new is not feasible:
      Assign score for failure and continue

    // 3. Local Search Phase (Intensification)
    If config.useLocalSearch and random() < config.localSearchIntensity:
      localSearch.run(s_new) // Apply 3-phase local search

    // 4. Acceptance Criterion
    improved = false
    If s_new.dominates(s_current):
      s_current = s_new
      Assign score for finding a new best solution
      improved = true
    Else:
      add_res = archive.tryAdd(s_new) // Add to Pareto archive
      If add_res is DOMINATING or NON_DOMINATED:
        s_current = s_new // Move search to new Pareto-optimal region
        Assign score for improving the archive
        improved = true
      Else: // s_new is dominated, use Simulated Annealing
        delta = calculateWeightedObjectiveDifference(s_new, s_current)
        If exp(-delta / currentTemperature) > random():
          s_current = s_new
          Assign score for accepted dominated solution
        Else:
          Assign score for rejected solution

    // 5. Stagnation & Perturbation
    If improved:
      iterationsWithoutImprovement = 0
    Else:
      iterationsWithoutImprovement++
    
    If iterationsWithoutImprovement > 2000:
      perturbationBoost = 1.5 // Increase destroy intensity
    Else If iterationsWithoutImprovement > 1000:
      perturbationBoost = 1.25
      currentTemperature = config.startTemperature * 0.8 // Reheating
      If random() < 0.2: s_current = archive.getRandomSolution(rng) // Jump
    Else:
      perturbationBoost = 1.0

    // 6. Update Temperature
    currentTemperature *= config.coolingRate

    // 7. Update Operator Weights & Check Hypervolume Convergence
    If iteration % config.segmentIterations == 0:
      destroyPool.updateWeights(config.decayParameter)
      repairPool.updateWeights(config.decayParameter)
      
      If checkHypervolumeConvergence(archive, lastMinVehicles, hvStagnationCount, previousHV):
        Break loop // Converged

  // 8. Optional: Scatter Search Intensification
  If config.useScatterSearch:
    scatterSearch.run(archive, *this)

  Return archive.getFront()
```

### 3.2. Initial Solution

A high-quality initial solution is generated using a problem-specific constructive heuristic. The heuristic adapts its strategy based on the instance type to improve the quality of the starting point.

-   **For R and RC instances (randomly distributed customers):** Customers are sorted by the tightness of their time windows (due date - ready time). This prioritizes customers with less scheduling flexibility.
-   **For C instances (clustered customers):** A Clarke-Wright Savings-based approach is used to pre-sort customers, naturally grouping geographically close customers.

The heuristic then greedily inserts customers from the sorted list into routes, performing look-ahead checks for feasibility. A fallback mechanism creates individual routes (with station assistance if needed) for any remaining unserved customers.

**Pseudo-code for Initial Solution Generation:**
```
Algorithm generateInitialSolution(Instance instance):
  Input: Problem Instance
  Output: Initial Solution (Solution object)

  sol = new Solution(instance)
  unservedCustomers = list of all customers

  // 1. Smart Sorting of Unserved Customers
  If instanceType is 'R' or 'RC':
    Sort unservedCustomers by Time Window Width (tightest first)
  Else (instanceType is 'C'):
    Sort unservedCustomers using Clarke-Wright Savings logic

  // 2. Main Construction Loop (Greedy Insertion)
  While unservedCustomers is not empty and not cannotServeMore:
    Create new Vehicle and new Route (currentRoute)
    
    While not routeFinished:
      bestCustId = -1
      bestScore = infinity

      For each custId in unservedCustomers:
        // Check feasibility (capacity, battery, time window)
        If not feasible: continue

        // Look-ahead check: Ensure return to depot or reachable station
        If not canReturnToDepotOrStation(...): continue

        // Calculate score (e.g., 70% distance, 30% urgency)
        score = calculateInsertionScore(...)
        If score < bestScore:
          bestScore = score
          bestCustId = custId

      If bestCustId != -1:
        Add bestCustId to currentRoute and update state
        Remove bestCustId from unservedCustomers
      Else: // No customer can be served
        If canChargeAtNearestStation(...):
          Add nearest station to currentRoute and update state
        Else:
          routeFinished = true

    If route is valid:
      sol.addRoute(currentRoute)
    Else: // Rollback if route became infeasible
      Return customers to unservedCustomers list

  // 3. Fallback for remaining unserved customers (individual routes)
  If unservedCustomers is not empty:
    For each custId in unservedCustomers:
      Try to create a single route (D -> C -> D)
      If not feasible, try with station assistance (D -> S -> C -> D)

  sol.evaluateRoutes()
  Return sol
```

### 3.3. Neighborhood Operators

A rich set of destroy and repair operators are implemented to ensure a diverse search.

#### 3.3.1. Destroy Operators

-   **UnifiedCostDestroy:**
    *   **Description:** Removes customers based on a unified cost metric. It can randomly focus on distance, time, energy, or workload balance. This helps remove "expensive" or "problematic" customers to create opportunities for better routing.
    *   **Pseudo-code:**
        ```
        Algorithm UnifiedCostDestroy.execute(Solution s, int n_to_remove, RandomEngine rng):
          unserved_customers = empty list
          candidate_customers = list of all customers in s
          
          For each customer c in candidate_customers:
            Calculate cost_c based on its route's properties (distance, time, energy, etc.)
            Store (cost_c, c.id) pairs

          Sort customers by cost_c in descending order

          For i = 1 to n_to_remove:
            Select customer c_remove with highest cost (or probabilistically from top)
            Remove c_remove from its route in s
            Add c_remove.id to unserved_customers

          Return unserved_customers
        ```

-   **ShawDestroy (Relatedness):**
    *   **Description:** Removes customers that are "related" to a randomly chosen seed customer. Relatedness is a weighted sum of proximity, time window similarity, demand difference, and whether they share the same nearest charging station. This creates a geographically and temporally concentrated "hole" in the solution.
    *   **Pseudo-code:**
        ```
        Algorithm ShawDestroy.execute(Solution s, int n_to_remove, RandomEngine rng):
          unserved_customers = empty list
          
          Select a random customer c_seed from s
          Remove c_seed from its route and add to unserved_customers

          While unserved_customers.size() < n_to_remove:
            Select a random customer c_current from unserved_customers
            
            For each customer c_other still in s:
              Calculate relatedness(c_current, c_other)
            
            Sort other customers by relatedness to c_current
            
            Select customer c_remove from top related candidates (probabilistically)
            Remove c_remove from its route and add to unserved_customers

          Return unserved_customers
        ```

-   **InefficientRouteRemoval:**
    *   **Description:** Targets and removes all customers from an entire route that is deemed inefficient. Inefficiency is scored based on having few customers, high waiting time, long distance per customer, or a high number of charging stops.
    *   **Pseudo-code:**
        ```
        Algorithm InefficientRouteRemoval.execute(Solution s, int n_to_remove, RandomEngine rng):
          unserved_customers = empty list
          
          For each route r in s:
            Calculate inefficiency_score(r)
          
          Sort routes by inefficiency_score descending

          Select route r_remove from top inefficient routes (probabilistically)
          
          For each customer c in r_remove:
            Add c.id to unserved_customers
          Remove r_remove from s

          Return unserved_customers
        ```

-   **RouteMergingDestroy:**
    *   **Description:** Aims to facilitate vehicle reduction. It selects two routes that are geographically close (based on centroids) and potentially mergeable (total demand < capacity), then removes all customers from both, challenging the repair operator to reconstruct them into a single, more efficient route.
    *   **Pseudo-code:**
        ```
        Algorithm RouteMergingDestroy.execute(Solution s, int n_to_remove, RandomEngine rng):
          unserved_customers = empty list
          
          Find best pair of routes (r1, r2) to merge based on proximity and capacity
          
          If no suitable pair found, fallback to random pair
          
          For each customer c in r1: Add c.id to unserved_customers
          For each customer c in r2: Add c.id to unserved_customers
          
          Remove r1 and r2 from s

          Return unserved_customers
        ```

-   **TargetedStationRemoval:**
    *   **Description:** Specifically removes charging stations from routes based on an inefficiency score. Stations that provide little charge, cause a large detour, or are redundant (e.g., right after the depot) are given a high score and are more likely to be removed.
    *   **Pseudo-code:**
        ```
        Algorithm TargetedStationRemoval.execute(Solution s, int n_to_remove, RandomEngine rng):
          // This operator removes stations, not customers.
          // The goal is to make the route infeasible, forcing the repair operator to find a better charging strategy.
          
          For each route r in s:
            For each station_node in r:
              Calculate inefficiency_score(station_node)
          
          Sort all station nodes in solution by score descending
          
          For i = 1 to (n_to_remove / 3): // Remove a smaller number of stations
            Select station s_remove from top candidates
            Remove s_remove from its route in s
            
          Return empty list (no customers removed)
        ```

#### 3.3.2. Repair Operators

-   **Regret-K Repair:**
    *   **Description:** A classic regret-based heuristic. For each unserved customer, it calculates the cost of inserting it into its `k` best positions. The customer with the highest "regret" (largest difference between its best and second-best insertion cost) is inserted first. This prioritizes "hard-to-place" customers. The implementation uses an adaptive `k` value.
    *   **Pseudo-code:**
        ```
        Algorithm RegretKRepair.execute(Solution s, List unserved_customers, RandomEngine rng, int K):
          While unserved_customers is not empty:
            best_customer_to_insert = null
            max_regret = -infinity
            
            For each customer c in unserved_customers:
              insertion_costs = list of costs for all possible insertions of c
              Sort insertion_costs ascending
              
              If insertion_costs.size() < K:
                regret = insertion_costs[0].cost
              Else:
                regret = insertion_costs[K-1].cost - insertion_costs[0].cost
              
              If regret > max_regret:
                max_regret = regret
                best_customer_to_insert = c
            
            If best_customer_to_insert is found:
              Find best insertion for best_customer_to_insert
              Insert it into the solution
              Remove from unserved_customers
            Else:
              Break // Cannot insert any remaining customer

          Return s
        ```

-   **AdaptiveInsertion:**
    *   **Description:** A consolidated greedy operator that randomly chooses its focus at each execution: minimizing distance increase, balancing workload (inserting into routes to make their duration closer to the average), or minimizing the maximum route time.
    *   **Pseudo-code:**
        ```
        Algorithm AdaptiveInsertion.execute(Solution s, List unserved_customers, RandomEngine rng):
          mode = randomly select one of {DISTANCE, WORKLOAD, MAXTIME}
          
          While unserved_customers is not empty:
            best_insertion_cost = infinity
            
            For each customer c in unserved_customers:
              For each possible insertion position p in s:
                insertion_cost = calculateCost(c, p, mode)
                If insertion_cost < best_insertion_cost:
                  Update best_insertion_cost and best_insertion_details
            
            If a best insertion was found:
              Apply the insertion
              Remove customer from unserved_customers
            Else:
              Create new route for the customer
        ```

-   **GreedyEnergyInsertion:**
    *   **Description:** A greedy operator that prioritizes insertions based on an energy-focused cost function, considering energy consumption, charging time, and penalties for requiring new charging stops.
    *   **Pseudo-code:**
        ```
        Algorithm GreedyEnergyInsertion.execute(Solution s, List unserved_customers, RandomEngine rng):
          While unserved_customers is not empty:
            best_energy_cost = infinity
            
            For each customer c in unserved_customers:
              For each possible insertion position p in s:
                energy_cost = calculateEnergyInsertionCost(c, p) // Focus on battery, charging
                If energy_cost < best_energy_cost:
                  Update best_energy_cost and best_insertion_details
            
            If a best insertion was found:
              Apply the insertion
              Remove customer from unserved_customers
            Else:
              Create new route for the customer
        ```

-   **ParetoFocusRepair:**
    *   **Description:** Similar to `AdaptiveInsertion`, but it strictly focuses on one objective (distance, time, or workload) chosen randomly, ignoring the impact on other objectives (while maintaining feasibility). This helps explore the extremes of the Pareto front.

-   **SmartStationRepair:**
    *   **Description:** An enhanced greedy operator that first attempts to insert customers without stations. If infeasible due to energy, it intelligently searches for the best station to add to the route to enable the insertion, considering detour cost.
    *   **Pseudo-code:**
        ```
        Algorithm SmartStationRepair.execute(Solution s, List unserved_customers, RandomEngine rng):
          For each customer c in unserved_customers:
            best_insertion = findBestDirectInsertion(c, s)
            
            If best_insertion is not feasible or too costly:
              best_station_assisted_insertion = findBestStationAssistedInsertion(c, s)
              If station-assisted is better:
                best_insertion = best_station_assisted_insertion
            
            If best_insertion is valid:
              Apply insertion (with or without station)
            Else:
              Create new route for c
        ```

-   **SmartTimeAwareStationRepair:**
    *   **Description:** A more advanced version of the above. It uses O(1) delta calculations and K-Nearest-Neighbor station searches to efficiently find the best station insertion. It can also detect "Free Charge" opportunities where charging can occur during existing slack time without increasing the total route duration.

### 3.4. Adaptive Weight Adjustment

The algorithm dynamically adjusts the selection probability (weights) of each operator. After a segment of iterations, the weights are updated based on the scores operators received. Operators that produce better solutions are rewarded with higher scores, increasing their chance of being selected in the future.

### 3.5. Acceptance Criterion & Multi-Objective Handling

A new solution `s_new` is compared to the current solution `s_current` using a multi-layered approach:

1.  **Dominance:** If `s_new` dominates `s_current` according to the hierarchical objectives, `s_current` is replaced by `s_new`.
2.  **Pareto Archive:** The `ParetoArchive` stores all non-dominated solutions found so far.
    -   **Bucketing:** Solutions are stored in "buckets" based on their vehicle count.
    -   **Hierarchical Pruning:** When a new solution with `V` vehicles is added, the archive **instantly and permanently deletes all buckets containing solutions with more than `V` vehicles**. This strictly enforces the primary objective and prevents the search from exploring inferior regions of the solution space.
    -   **Crowding Distance:** If a bucket exceeds its maximum size, it is pruned by removing the solution in the most "crowded" region of the objective space, preserving diversity on the front (based on NSGA-II's crowding distance metric).
3.  **Simulated Annealing (SA):** If `s_new` is dominated by `s_current`, it can still be accepted based on a probability `exp(-delta / T)`, where `delta` is the degradation in a weighted-sum of the objectives and `T` is the current "temperature". This allows the algorithm to escape local optima.

#### 3.5.1. Early Stopping (Hypervolume Convergence)

To avoid unnecessary iterations, the ALNS uses a **Hypervolume-based early stopping mechanism**:
- At the end of each segment, the 3D Hypervolume of the current Pareto Archive is calculated (using Distance, Gini, and MaxTime for the lowest vehicle count found).
- A fixed reference box is established when a new best vehicle count is found, ensuring that HV improvements are genuine and not due to normalization changes.
- If the relative improvement in Hypervolume falls below a threshold (`hvImprovementThreshold`) for a consecutive number of segments (`hvStagnationLimit`), the algorithm assumes the Pareto Front has converged and terminates early.

### 3.6. Local Search Module

The ALNS integrates a powerful, three-phase local search module to intensify the search. It employs a "First Improvement" strategy, applying the first improving move found.

**Key Performance Optimizations:**

-   **Tiered Filtering:** A multi-level check system to quickly prune unpromising moves (`Route::canPossiblyInsert`, `Route::fastForwardCheck`, `Route::checkInsertionCost`).
-   **Static Move Descriptor (SMD):** A single `MoveDescriptor` object is reused across all search operations to avoid repeated memory allocations.
-   **Search Context Cache:** Caches route centroids and neighbor lists, which are only recomputed when the solution changes.
-   **Granular Neighborhoods:** Restricts the search for inter-route moves to routes that are geographically close.
-   **K-Nearest Neighbors (KNN) Cache:** Pre-calculates the K-nearest neighbors for each customer to focus the search on promising local regions.
-   **Adaptive Sizing:** Dynamically adjusts the size of neighborhoods based on recent search success.

**Local Search Phases & Operators:**

1.  **Phase 1: Distance Optimization (VND):** A Variable Neighborhood Descent that cycles through the following operators:
    -   **Relocate (1-Opt):** Moves a single customer to another position (intra- or inter-route).
        ```
        Algorithm searchRelocate(solution):
          For each customer node_i in solution:
            For each possible new position j for node_i:
              // Tiered Filtering:
              If not canPossiblyInsert(node_i, j): continue
              delta = evaluateRelocateDelta(node_i, j)
              If delta >= 0: continue
              
              // Full Evaluation:
              evaluateMove(RELOCATE, node_i, j)
              If move is feasible and improves objective:
                applyMove(RELOCATE, node_i, j) // First Improvement
                Return true
        ```
    -   **2-Opt:** Reverses a segment within a single route to untangle paths.
        ```
        Algorithm searchTwoOpt(solution):
          For each route r in solution:
            For each pair of edges (i, i+1) and (j, j+1) in r:
              If reversing segment [i+1, j] improves distance:
                evaluateMove(TWO_OPT, i, j)
                If move is feasible and improves objective:
                  applyMove(TWO_OPT, i, j) // First Improvement
                  Return true
        ```
    -   **Swap:** Exchanges the positions of two customers (intra- or inter-route).
        ```
        Algorithm searchSwap(solution):
          // Intra-route swaps
          For each route r:
            For each pair of customers (i, j) in r:
              If swapping i and j improves objective:
                applyMove(INTRA_SWAP, i, j) and Return true
          
          // Inter-route swaps
          For each pair of routes (r1, r2):
            If routes are close (granular filter):
              For each pair of customers (i in r1, j in r2):
                If customers are close (KNN filter):
                  If swapping i and j improves objective:
                    applyMove(INTER_SWAP, i, j) and Return true
        ```
    -   **Or-Opt:** Moves a contiguous segment of 2-3 customers to another position.

2.  **Phase 2: Charging Optimization:** A set of operators run periodically to improve energy efficiency:
    -   `removeRedundantStations`: Removes stations that are unnecessary.
    -   `repositionStations`: Tries to move a station to a better location.
    -   `searchStationSwap`: Replaces a station with a more "centroid-optimal" one.
    -   `optimizeChargingAmounts`: Removes stations with negligible charge or those that are strategically redundant.

3.  **Phase 3: Vehicle Reduction:** Aggressive operators run periodically or when the search stagnates:
    -   `runSmartMultiRouteMerge`: Attempts to merge two small, nearby routes.
    -   `tryEliminateSmallestRoute`: Attempts to remove the route with the fewest customers by re-inserting its customers into other routes.

**Specialized Heuristics:**

-   **Energy Boost Relocate:** If a `Relocate` move is beneficial for distance but fails due to energy, this helper function attempts to salvage the move by inserting a charging station into the target route to restore feasibility.

### 3.7. Perturbation

To escape deep local optima during periods of stagnation, several perturbation mechanisms are used:
-   **Reheating:** The Simulated Annealing temperature is increased.
-   **Archive Jump:** The current solution is replaced with a random solution from the Pareto archive.
-   **Increased Destruction:** The number of customers to remove is temporarily increased.

### 3.8. Scatter Search (Optional Intensification)

The framework includes an optional `ScatterSearch` module that can be run after the main ALNS loop for further intensification.
-   **Reference Set:** It builds a reference set of high-quality (Tier 1) and diverse (Tier 2, based on crowding distance) solutions from the final Pareto Archive.
-   **Combination Method:** It uses **Path Relinking** to generate new solutions by gradually transforming one parent solution into another, exploring the path between them.
-   **Improvement:** New solutions generated via Path Relinking are improved using a short run of the ALNS algorithm before being submitted to the Pareto Archive.
