# Scientific Report: A Multi-Objective Adaptive Large Neighborhood Search for the Electric Vehicle Routing Problem with Time Windows (EVRPTW)

## Abstract

This document provides a detailed description of a sophisticated solver for the Electric Vehicle Routing Problem with Time Windows (EVRPTW). The problem is modeled as a multi-objective optimization task with a hierarchical objective function designed to primarily minimize the number of vehicles, secondarily minimize total travel distance, and finally improve solution quality by balancing workload and minimizing the maximum route time. The implemented solution is based on the Adaptive Large Neighborhood Search (ALNS) metaheuristic, enhanced with a sophisticated Pareto archive, a Simulated Annealing-based acceptance criterion, and a powerful, multi-phase local search module for intensification. The framework also includes advanced features like Hypervolume-based convergence tracking.

---

## 1. Problem Definition

The Electric Vehicle Routing Problem with Time Windows (EVRPTW) is an extension of the classical Vehicle Routing Problem (VRP). It involves designing a set of optimal routes for a fleet of electric vehicles (EVs) to serve a group of customers, subject to various real-world constraints.

- A central depot serves as the starting and ending point for all vehicle routes.
- Each customer has a specific demand and a time window within which service must begin.
- The electric vehicles have a limited carrying capacity and a finite battery range.
- A set of charging stations are available, which can be visited by vehicles to recharge their batteries. These stations also have their own operational time windows.

The primary goal is to find a feasible set of routes that serves all customers while respecting all constraints and optimizing the given objectives.

### 1.1. Objectives

The problem is treated as a **hierarchical multi-objective optimization problem**. The objectives are prioritized as follows:

1.  **Primary Objective:** Minimize the total number of vehicles used. `(Minimize |K|)`
2.  **Secondary Objective:** Minimize the total travel distance of all routes. `(Minimize Σ TotalDistance_k)`
3.  **Tertiary Objective (1):** Minimize the workload imbalance between routes, measured by the **variance of active route times**. A lower variance indicates a more balanced workload. `(Minimize Var(ActiveTime_k))`
4.  **Tertiary Objective (2):** Minimize the completion time of the longest route (makespan). `(Minimize Max(TotalTime_k))`

A solution A is considered to dominate solution B if it is better in at least one objective without being worse in any other, following the strict hierarchical order. For example, a solution with fewer vehicles is always better, regardless of other objective values.

## 2. Mathematical Formulation

*(This section remains unchanged as the mathematical model is standard. The novelty lies in the solution methodology.)*

### 2.1. Sets and Indices
- `D = {0}`: The set containing the central depot.
- `C = {1, ..., N}`: The set of customers.
- `S = {N+1, ..., N+M}`: The set of charging stations.
- `V = D ∪ C ∪ S`: The set of all nodes.
- `V' = C ∪ S`: The set of all possible visit locations.
- `K`: The set of available homogeneous electric vehicles.

### 2.2. Parameters
- `d_ij`: Distance between node `i` and node `j`.
- `t_ij`: Travel time between node `i` and node `j`.
- `q_i`: Demand of customer `i`.
- `[e_i, l_i]`: Time window for node `i`.
- `s_i`: Service time required at customer `i`.
- `C_k`: Maximum cargo capacity of vehicle `k`.
- `Q_k`: Maximum battery capacity of vehicle `k`.
- `h`: Energy consumption rate.
- `g_j`: Charging rate at station `j`.

### 2.3. Decision Variables
- `x_ijk`: Binary, 1 if vehicle `k` travels from `i` to `j`.
- `A_ik`: Arrival time of vehicle `k` at node `i`.
- `L_ik`: Remaining cargo load of vehicle `k` at node `i`.
- `B_ik`: Remaining battery level of vehicle `k` at node `i`.
- `c_jk`: Amount of energy charged to vehicle `k` at station `j`.
- `u_k`: Binary, 1 if vehicle `k` is used.

### 2.4. Objective Function
Minimize `(Z_1, Z_2, Z_3, Z_4)` where:
`Z_1 = Σ_{k ∈ K} u_k`
`Z_2 = Σ_{i,j,k} d_ij * x_ijk`
`Z_3 = Variance({ActiveTime_k | k ∈ K, u_k=1})`
`Z_4 = Max_{k ∈ K} (CompletionTime_k)`

### 2.5. Constraints
*(Standard VRP, TW, Capacity, and Energy constraints apply.)*

## 3. Solution Methodology: Adaptive Large Neighborhood Search (ALNS)

The problem is solved using a sophisticated ALNS metaheuristic tailored for hierarchical multi-objective optimization.

### 3.1. Overall Framework

The ALNS algorithm starts with an initial solution and iteratively tries to improve it. In each iteration, a portion of the current solution is "destroyed" and then "repaired". The choice of destroy and repair methods is guided by an adaptive weight adjustment mechanism that rewards operators for finding high-quality solutions.

**Pseudo-code for ALNS Main Loop:**

```
Algorithm ALNSSolver.solve():
  Input: Instance, ALNSConfig config
  Output: ParetoArchive (set of non-dominated solutions)

  s_current = generateInitialSolution()
  archive.tryAdd(s_current)
  currentTemperature = config.startTemperature
  iterationsWithoutImprovement = 0
  perturbationBoost = 1.0

  // HV-based convergence state
  previousHV = 0.0
  hvStagnationCount = 0
  lastMinVehicles = s_current.getTotalVehicles()

  For iteration = 1 to config.maxIterations:
    s_new = s_current.copy() // Uses SolutionPool for efficiency

    // 1. Destroy Phase
    n_to_remove = calculateNodesToRemove(perturbationBoost)
    destroy_op = destroyPool.select(rng)
    unserved_custs = destroy_op.execute(s_new, n_to_remove, rng)

    // 2. Repair Phase
    repair_op = repairPool.select(rng)
    repair_op.execute(s_new, unserved_custs, rng)

    s_new.evaluateRoutes() // Re-evaluate feasibility and all objectives

    If s_new is not feasible:
      Assign score for failure and continue

    // 3. Local Search Phase (Intensification)
    If config.useLocalSearch and random() < config.localSearchIntensity:
      localSearch.run(s_new) // Apply 3-phase local search

    // 4. Acceptance Criterion
    improved = false
    If s_new.dominates(s_current):
      s_current = s_new
      Assign score for finding a new best solution
      improved = true
    Else:
      add_res = archive.tryAdd(s_new) // Add to Pareto archive
      If add_res is DOMINATING or NON_DOMINATED:
        // Do not force s_current = s_new, let SA decide to maintain diversity
        Assign score for improving the archive
        improved = true

      // If s_new is dominated or identical, use Simulated Annealing
      delta = calculateWeightedObjectiveDifference(s_new, s_current)
      If exp(-delta / currentTemperature) > random():
        s_current = s_new
        Assign score for accepted non-improving solution
      Else:
        Assign score for rejected solution

    // 5. Stagnation & Perturbation
    If improved:
      iterationsWithoutImprovement = 0
    Else:
      iterationsWithoutImprovement++

    If iterationsWithoutImprovement > 1000:
      perturbationBoost = 1.25
      currentTemperature = config.startTemperature * 0.8 // Reheating
      If random() < 0.2: s_current = archive.getRandomSolution(rng) // Jump
    Else:
      perturbationBoost = 1.0

    // 6. Update Temperature
    currentTemperature *= config.coolingRate

    // 7. Update Operator Weights & Check Hypervolume Convergence
    If iteration % config.segmentIterations == 0:
      destroyPool.updateWeights(config.decayParameter)
      repairPool.updateWeights(config.decayParameter)

      If checkHypervolumeConvergence(archive, lastMinVehicles, hvStagnationCount, previousHV):
        Break loop // Converged

  Return archive.getFront()
```

### 3.2. Initial Solution

A high-quality initial solution is generated using a **multi-start constructive heuristic**. The algorithm generates multiple initial solutions using different customer ordering strategies and picks the best one (minimum vehicles, then minimum distance) to start the ALNS search.

The implemented ordering strategies are:
-   **Sweep Order:** Sorts customers by their polar angle relative to the depot, which is effective for clustered instances.
-   **Nearest Neighbor Order:** Greedily builds a single path by always moving to the closest unvisited customer.
-   **Earliest Deadline First (EDF):** Sorts customers by their due date, prioritizing those with urgent deadlines.
-   **Tightest Time Window First:** Sorts customers by the width of their time window (due date - ready time), prioritizing those with the least scheduling flexibility.

For each ordering, a greedy insertion heuristic is used to build routes. It iterates through the sorted customer list, attempting to insert each customer into the best feasible position in an existing route. If no feasible position is found, it tries to open a new route. Station-assisted insertions are used as a fallback to ensure feasibility.

### 3.3. Neighborhood Operators

A rich set of destroy and repair operators are implemented to ensure a diverse search. The following sections provide detailed pseudocode for each operator, reflecting the C++ implementation.

#### 3.3.1. Destroy Operators

These operators deconstruct a solution by removing a set of customers, who are then added to a list of "unserved" customers to be re-inserted by a repair operator.

-   **ShawDestroy (Relatedness Removal)**: Removes customers that are similar to each other, aiming to remove a cluster of related customers that can then be re-inserted in a more optimal way.

    ```
    Algorithm ShawDestroy(solution, nodesToRemove):
      1. Build a list of all customers currently in the solution.
      2. Select a "seed" customer, prioritizing those with the tightest time windows.
      3. Add the seed customer to the `removed` list.
      4. While `removed.size() < nodesToRemove`:
         a. Pick a random customer `r` from the `removed` list.
         b. For each customer `c` not yet removed:
            i. Calculate `relatedness(r, c)`. Relatedness is a weighted sum of:
               - Normalized distance between `r` and `c`.
               - Normalized difference in time window start times.
               - Normalized difference in demand.
               - Whether `r` and `c` are in the same route.
               - Whether `r` and `c` share the same nearest charging station.
         c. Select the next customer to remove using a randomized, deterministic selection (the customer with the lowest relatedness score is most likely to be chosen).
         d. Add the selected customer to the `removed` list.
      5. Rebuild the routes in the solution to remove the selected customers.
      6. Return the `removed` list.
    ```

-   **InefficientRouteRemoval**: Removes one or more entire routes that are considered inefficient, forcing the repair operator to repack all their customers.

    ```
    Algorithm InefficientRouteRemoval(solution, nodesToRemove):
      1. Calculate average statistics across all active routes (customers per route, distance per customer, wait time per customer).
      2. For each route, calculate an "inefficiency score" based on:
         - Relative size (smaller routes get a higher score).
         - Relative efficiency (routes with higher distance/customer get a higher score).
         - Relative wait time.
         - Penalties for bottlenecks and station overhead.
         - Bonuses for time window coverage and "energy portability" (customers are close to the depot).
      3. Use a tournament selection to choose one or more of the highest-scoring (most inefficient) routes.
      4. Remove all customers from the selected routes.
      5. Remove the now-empty routes from the solution.
      6. Return the list of all removed customers.
    ```

-   **RouteMergingDestroy**: Aims to reduce the number of vehicles by removing two entire routes that are geographically close and could potentially be merged.

    ```
    Algorithm RouteMergingDestroy(solution, nodesToRemove):
      1. Identify all pairs of active routes (r1, r2).
      2. For each pair, check if they can be potentially merged:
         - Is `total_demand(r1) + total_demand(r2)` within a relaxed capacity limit?
         - Do their customers' time windows have a reasonable degree of overlap?
      3. Calculate the Euclidean distance between the centroids of all mergeable pairs.
      4. Select the pair of routes with the smallest centroid distance.
      5. Remove all customers from both selected routes.
      6. Remove the empty routes from the solution.
      7. Return the list of all removed customers.
    ```

-   **TimeSlackDestroy**: Removes customers based on their time-related criticality, focusing on those whose removal would create the most scheduling flexibility.

    ```
    Algorithm TimeSlackDestroy(solution, nodesToRemove):
      1. For each route, compute detailed timing data: arrival times, service starts, and slack for each customer.
      2. Compute the Forward Time Slack (FTS) for each customer, which is the minimum slack of all subsequent customers in the same route segment (between stations).
      3. For each customer `c`, calculate a "liberation score" based on:
         - FTS Criticality: A measure of how many preceding customers are constrained by `c`'s time window.
         - Actual Time Saved: The real reduction in route completion time if `c` is removed.
         - Waiting time at `c`.
      4. Create a list of all customers, sorted by their liberation score.
      5. Select `nodesToRemove` customers from the list using a randomized, deterministic selection.
      6. Remove the selected customers and update the routes.
      7. Return the list of removed customers.
    ```


-   **RandomRemoval**: Removes a random set of customers to diversify the search.

    ```
    Algorithm RandomRemoval(solution, nodesToRemove):
      1. Collect all customers from all routes.
      2. Shuffle the list of customers randomly.
      3. Select the first `nodesToRemove` customers from the shuffled list.
      4. Remove the selected customers from their routes.
      5. Return the list of removed customers.
    ```

-   **RandomRouteRemoval**: Removes all customers from a single, randomly chosen route.

    ```
    Algorithm RandomRouteRemoval(solution, nodesToRemove):
      1. Create a list of all active routes.
      2. Select one route using a weighted random selection, where smaller routes have a higher probability of being chosen.
      3. Remove all customers from the selected route.
      4. Remove the empty route from the solution.
      5. Return the list of removed customers.
    ```

#### 3.3.2. Repair Operators

These operators take the list of unserved customers and re-insert them into the solution's routes or into new routes.

-   **AdaptiveInsertion**: A flexible greedy operator that adapts its insertion criteria based on the overall search objective, guided by a "weight hint" from the ALNS solver.

    ```
    Algorithm AdaptiveInsertion(solution, unservedCustomers):
      1. Determine the insertion `Mode` based on the weight hint (e.g., DISTANCE_FOCUSED, VEHICLE_PACKING, WORKLOAD_FOCUSED).
      2. Sort `unservedCustomers` by time window tightness (tightest first).
      3. For each customer `c`:
         a. Find the best insertion position for `c` across all existing routes. The "cost" of an insertion is calculated based on the current `Mode`:
            - **DISTANCE_FOCUSED**: Cost is `deltaDistance`.
            - **VEHICLE_PACKING**: Cost is `deltaDistance` minus a large bonus for inserting into routes with high time utilization and energy slack. This encourages packing customers into busy routes.
            - **WORKLOAD_FOCUSED**: Cost is a normalized sum of the new route's duration and the `deltaDistance`.
            - **MAXTIME_FOCUSED**: Cost is based on the increase in the makespan (longest route time), plus `deltaDistance`.
         b. If the `Mode` is `VEHICLE_PACKING` or if no direct insertion was found, also evaluate station-assisted insertions (inserting both the customer and a nearby charging station).
         c. If a feasible insertion is found, apply it.
         d. Otherwise, create a new route for the customer, adding a station if necessary.
    ```

-   **GreedyEnergyInsertion**: A greedy operator that prioritizes insertions based on an energy-focused cost function.

    ```
    Algorithm GreedyEnergyInsertion(solution, unservedCustomers):
      1. Sort `unservedCustomers` by energy difficulty (customers farther from the depot are harder to serve and are inserted first).
      2. For each customer `c`:
         a. Find the best insertion position for `c` across all existing routes.
         b. The insertion "cost" is a complex metric that includes:
            - The increase in energy consumption.
            - A penalty for any additional charging required.
            - A penalty if the insertion is likely to require a new station visit.
            - A penalty for inserting into an energy "bottleneck" (a point in the route with low remaining battery).
         c. If a feasible insertion is found, apply it.
         d. If no direct insertion is feasible, attempt a station-assisted insertion.
         e. If all else fails, create a new route for the customer.
    ```

-   **SmartStationRepair**: An enhanced greedy operator that intelligently searches for station insertions only when necessary.

    ```
    Algorithm SmartStationRepair(solution, unservedCustomers):
      1. Sort `unservedCustomers` by time window tightness.
      2. For each customer `c`:
         a. First, find the best insertion position for `c` assuming **no station is added**.
         b. Then, for every possible insertion position, evaluate the cost of inserting `c` **with the help of a nearby station**. This involves checking top-K nearest stations for both `[station, customer]` and `[customer, station]` patterns.
         c. Compare the best direct insertion with the best station-assisted insertion and apply the one with the lowest cost (`deltaDistance`).
         d. If no insertion is found, create a new route for the customer, with a station if needed.
    ```


-   **ChargingAwareRouteBuilder**: A powerful, constructive operator that attempts to build one or more entirely new, highly efficient routes from the pool of unserved customers.

    ```
    Algorithm ChargingAwareRouteBuilder(solution, unservedCustomers):
      1. While `unservedCustomers` is not empty:
         a. Select a "seed" customer (e.g., the one with the tightest time window).
         b. **Launch a beam search** to construct the best possible single route that includes the seed customer and as many other unserved customers as possible.
            i. The search builds route "segments" between charging stations or the depot.
            ii. An "inner" beam search finds the best sequence of customers within a segment.
            iii. An "outer" beam search finds the best sequence of segments to form a complete route.
         c. If a valid, non-empty route is constructed, add it to the solution and remove its customers from the `unservedCustomers` list.
         d. If the beam search fails, or if customers remain after the search, fall back to a simpler greedy insertion (like `AdaptiveInsertion`) to place the remaining customers.
    ```

### 3.4. Adaptive Weight Adjustment

The algorithm dynamically adjusts the selection probability (weights) of each operator. After a segment of iterations, the weights are updated based on the scores operators received. Operators that produce better solutions (dominating, non-dominated, or accepted by SA) are rewarded with higher scores, increasing their chance of being selected in the future.

### 3.5. Acceptance Criterion & Multi-Objective Handling

A new solution `s_new` is compared to the current solution `s_current` using a multi-layered approach:

1.  **Dominance:** If `s_new` dominates `s_current` according to the hierarchical objectives, `s_current` is replaced by `s_new`.
2.  **Pareto Archive:** The `ParetoArchive` stores all non-dominated solutions found so far.
    -   **Bucketing:** Solutions are stored in "buckets" based on their vehicle count.
    -   **Hierarchical Pruning:** When a new solution with `V` vehicles is added, the archive **instantly and permanently deletes all buckets containing solutions with more than `V` vehicles**. This strictly enforces the primary objective.
    -   **Crowding Distance:** If a bucket exceeds its maximum size, it is pruned by removing the solution in the most "crowded" region of the objective space (based on NSGA-II's crowding distance metric).
3.  **Simulated Annealing (SA):** If `s_new` is not better than `s_current`, it can still be accepted based on a probability `exp(-delta / T)`, where `delta` is the degradation in a weighted-sum of the objectives and `T` is the current "temperature". This allows the algorithm to escape local optima.

#### 3.5.1. Early Stopping (Hypervolume Convergence)

To avoid unnecessary iterations, the ALNS uses a **Hypervolume-based early stopping mechanism**:
- At the end of each segment, the 3D Hypervolume of the current Pareto Archive is calculated (using Distance, Workload Variance, and MaxTime for the lowest vehicle count found).
- If the relative improvement in Hypervolume falls below a threshold (`hvImprovementThreshold`) for a consecutive number of segments (`hvStagnationLimit`), the algorithm assumes the Pareto Front has converged and terminates early. This is reset whenever a solution with fewer vehicles is found.

## 3.6. Local Search Module

The ALNS integrates a powerful, three-phase local search module to intensify the search. It employs a "First Improvement" strategy, successfully returning immediately upon applying the first improving move found to radically accelerate the intensification process and loop turnaround.

### 3.6.1. Key Performance Optimizations

-   **Tiered Filtering:** A meticulous multi-level check system is implemented to extremely fast-prune unpromising moves prior to executing heavy evaluate methods.
    -   **Tier 3 (Bounding/Capacity Check):** `Route::quickCapacityCheck`, `Route::canPossiblyInsert`, and flat cache O(1) `demandById_` arrays are utilized. Relocate and swap operations immediately perform boundary tests on capacity (and optionally, basic TW start logic) to prune inherently infeasible segments.
    -   **Tier 2 (Distance/Fast-Path Delta):** Moves calculate O(1) bounding distance metrics to compute the potential `distDelta`. E.g., relocations, swaps, 2-opts, or cross exchanges reject structurally heavier paths prior to route object copy operations, saving immense overhead.
    -   **Tier 1 (Full Evaluation):** `evaluateMove()` calls `Route::evaluate` on minimal route copies exclusively if filters signal an improving heuristic state.
-   **O(1) Memory Lookups & Buffers:** Advanced structural flat arrays (`nodeTypeById_`, `readyTimeById_`, `dueDateById_`, `serviceTimeById_`, and `demandById_`) replace complex graph accessors. Redundant allocations are heavily avoided via `thread_local` cache arrays or vectors indexing direct nodes (especially for KNN results or swap dedup bits).
-   **Static Move Descriptor (SMD) pattern:** Operator evaluations utilize constant memory descriptor instances avoiding re-allocation dynamically across millions of iterations.
-   **Granular & KNN-based Neighborhoods:** The search space for inter-route and node logic is drastically bounded.
    -   **Granular Neighborhoods:** The `SearchContext` intelligently caches route centroids. Dual-route operators (e.g., `Swap`, `Relocate`, `Inter-2-opt`, `Or-opt`) examine only proximal routes utilizing pre-calculated adaptive `distanceThreshold` mapping.
    -   **K-Nearest Neighbors (KNN) Vector Check:** For insertion paths mapped per node, a threaded fast vector ensures KNN neighborhood pruning bounds loop ranges to explicitly related nearby nodes.
-   **Adaptive Neighborhood Sizing:** `maxNodesToCheck_` or `maxSwapAttempts_` shrinks progressively on improvement successes out of local focus and dilates on iteration failure states, controlling the strictness limit iteratively.

### 3.6.2. Local Search Phases & Operators

The local search runs three defined phases in loop iterations mapping to VND logic and vehicle-centric minimization.

1.  **Phase 1: Distance Optimization (VND):** A fast variable descent passing sequentially among intensive spatial operators, immediately restarting from index zero entirely upon a first improvement finding.
        ```
        Algorithm runDistanceOptimization(solution):
          localImproved = true
          While localImproved:
            localImproved = false
            If searchRelocate(solution) then localImproved = true; continue
            If searchSwap(solution) then localImproved = true; continue
            If searchIntraTwoOpt(solution) then localImproved = true; continue
            If searchInterTwoOpt(solution) then localImproved = true; continue
            If searchOrOpt(solution) then localImproved = true; continue
            If searchCrossExchange(solution) then localImproved = true; continue
          Return improved
        ```
    -   **Relocate (1-Opt):** Moves a single node intra- or inter-route. Evaluates bounded delta quickly.
        ```
        Algorithm searchRelocate(solution, context):
          For each route r1 in solution:
            For each customer node_i in r1 (ranked by removal savings):
              // Granular Filter (Route-level proximity bounds)
              For each route r2 in context.neighborLists[r1]:
                // KNN Filter (Node-level explicitly near neighbors cache)
                For each candidate position j in findBestInsertionPositions_KNN(r2, node_i, context):

                  // Tier 3 Filter: Capacity Check & Constraint verification
                  If r2.getTotalDemand() + demandById_[node_i] > r2.Capacity: continue
                  If not r2.canPossiblyInsert(node_i, j): continue

                  // Tier 2 Filter: Fast Path Evaluation Delta O(1)
                  delta = calculateDeltaDistance(node_i, j, r1, r2)
                  If delta >= 0: continue

                  // Tier 1: Full Route Simulation Copy Evaluation
                  evaluateMove(RELOCATE, node_i, j, r1, r2)
                  If move is feasible and improves objective (First Improvement):
                    applyMove(...)
                    Return true
                  Else If move failed strictly due to energy limit:
                    If tryRelocateWithEnergyBoost(...): // Restorative Heuristic
                      Return true
        ```
    -   **Swap:** Exchanges nodes internally in a single route or pairs dynamically between routes with similar Tier filtering (Capacity pre-checks are pivotal).
        ```
        Algorithm searchSwap(solution, context):
          For each route r1 in solution:
            For each customer node_i in r1:
              For each route r2 in context.neighborLists[r1]:
                // Inter-route Capacity pre-check before node looping
                If r1 != r2 and (r1.totalDemand - demand[i] + min_demand > r1.Capacity or r2.totalDemand + demand[i] - max_demand > r2.Capacity):
                   continue

                For each candidate node_j in r2 (using KNN filter):
                  // Tier 3 Filter: Strict Capacity check
                  If r1 != r2 and (r1.totalDemand - demand[i] + demand[j] > r1.Capacity or r2.totalDemand - demand[j] + demand[i] > r2.Capacity):
                    continue

                  // Tier 2 Filter: O(1) distance delta
                  delta = calculateSwapDelta(node_i, node_j, r1, r2)
                  If delta >= 0: continue

                  // Tier 1: Full Route Simulation
                  evaluateMove(SWAP, node_i, node_j, r1, r2)
                  If feasible and improves (First Improvement):
                     applyMove(...)
                     Return true
        ```
    -   **2-Opt (Intra-route):** Untangles crossing node segments through segment reversals conditionally tested for raw distance drops prior to simulating.
    -   **Inter-2-Opt (Cross-route):** Segment tail exchanges across routes. Splices are processed rapidly using block assignments. Evaluated through Granular bound limits.
    -   **Or-Opt:** Sequential contiguous segment moves of sizes 1, 2, or 3 across route paths. Extremely powerful but bounded by extensive pre-checks.
    -   **Cross-Exchange:** Dynamically trades disparate contiguous sequences of varying lengths across differing routes. Pre-bounds check capacity limitations entirely before deep segment building.

2.  **Phase 2: Charging Optimization:** Operates rhythmically per loop constants to clean, reduce, or shift energy dependencies.
    -   `removeRedundantStations`: Examines nodes and evicts instances where battery feasibility still stands post-removal (saving detour detriments).
    -   `repositionStations`: Swaps used stations dynamically for closer structural alternatives using spatial instances logic.
    -   `searchStationSwap`: Compares charge centroids globally in routes to swap inefficient stations toward mass centers.

3.  **Phase 3: Vehicle Reduction:** Continually iterates when improvements land (Phase 1 success) aiming forcefully to strip route containers. Multi-phase approach:
    -   `ejectionChain`: Advanced ejection strategy executing a tree-chain sequence displacing up to depth iterations to force-pack a target customer from a victim route into otherwise fully loaded vehicles.
    -   `tryEliminateSmallestRoute`: Attempts destruction natively of the least populated route through cascading unserved placements.
    -   `runSmartMultiRouteMerge`: Tries consolidating two (or multi) geographically close suboptimal routes fully together intelligently via KNN density.

### 3.6.3. Specialized Heuristics

-   **Energy Boost Relocate:** Triggered predominantly when spatial distance gains are heavy, yet battery is infeasible. Dynamically runs algorithms inserting required station waypoints into target route vectors sequentially to rescue and finalize the swap.
        ```
        Algorithm tryRelocateWithEnergyBoost(node_i, r2):
          Find nearest station S from node_i
          For each valid adjacent segment logically preceding/following node_i:
              Simulate route: insert S, insert node_i
              If S makes route feasible in energy without breaking TWs:
                   Return True
          Return False
        ```

### 3.7. Perturbation

To escape deep local optima during periods of stagnation, several perturbation mechanisms are used:
-   **Reheating:** The Simulated Annealing temperature is dynamically increased based on cooling multipliers.
-   **Archive Jump:** The current active local minima solution is replaced outright with an archived, non-dominated diverse frontier solution structure.
-   **Increased Destruction Limit:** Number of randomized operators dynamically pulls increased node boundaries temporally to disperse path sequences further.
