\begin{abstract}
This document provides a detailed description of a sophisticated solver for the Electric Vehicle Routing Problem with Time Windows (EVRPTW). The problem is modeled as a multi-objective optimization task with a hierarchical objective function designed to primarily minimize the number of vehicles, secondarily minimize total travel distance, and finally improve solution quality by balancing workload and minimizing the maximum route time. The implemented solution is based on the Adaptive Large Neighborhood Search (ALNS) metaheuristic, enhanced with a sophisticated Pareto archive, a Simulated Annealing-based acceptance criterion, and a powerful, multi-phase local search module for intensification. The framework also includes advanced features like Hypervolume-based convergence tracking and an optional Scatter Search phase for deep exploration.
\end{abstract}

\section{Problem Definition}

The Electric Vehicle Routing Problem with Time Windows (EVRPTW) is an extension of the classical Vehicle Routing Problem (VRP). It involves designing a set of optimal routes for a fleet of electric vehicles (EVs) to serve a group of customers, subject to various real-world constraints.
\begin{itemize}
    \item A central depot serves as the starting and ending point for all vehicle routes.
    \item Each customer has a specific demand and a time window within which service must begin.
    \item The electric vehicles have a limited carrying capacity and a finite battery range.
    \item A set of charging stations are available, which can be visited by vehicles to recharge their batteries. These stations also have their own operational time windows.
\end{itemize}
The primary goal is to find a feasible set of routes that serves all customers while respecting all constraints and optimizing the given objectives.

\subsection{Objectives}

The problem is treated as a \textbf{hierarchical multi-objective optimization problem}. The objectives are prioritized as follows:
\begin{enumerate}
    \item \textbf{Primary Objective:} Minimize the total number of vehicles used. \texttt{(Minimize |K|)}
    \item \textbf{Secondary Objective:} Minimize the total travel distance of all routes. \texttt{(Minimize $\Sigma$ TotalDistance_k)}
    \item \textbf{Tertiary Objective (1):} Minimize the workload imbalance between routes, measured by the Gini Coefficient of active route times. A lower Gini coefficient (closer to 0) indicates a more balanced workload. \texttt{(Minimize Gini(ActiveTime_k))}
    \item \textbf{Tertiary Objective (2):} Minimize the completion time of the longest route (makespan). \texttt{(Minimize Max(TotalTime_k))}
\end{enumerate}
A solution A is considered to dominate solution B if it is better in at least one objective without being worse in any other, following the strict hierarchical order. For example, a solution with fewer vehicles is always better, regardless of other objective values.

\section{Mathematical Formulation}

\textit{(This section remains unchanged as the mathematical model is standard. The novelty lies in the solution methodology.)}

\subsection{Sets and Indices}
\begin{itemize}
    \item $D = \{0\}$: The set containing the central depot.
    \item $C = \{1, ..., N\}$: The set of customers.
    \item $S = \{N+1, ..., N+M\}$: The set of charging stations.
    \item $V = D \cup C \cup S$: The set of all nodes.
    \item $V' = C \cup S$: The set of all possible visit locations.
    \item $K$: The set of available homogeneous electric vehicles.
\end{itemize}

\subsection{Parameters}
\begin{itemize}
    \item $d_{ij}$: Distance between node $i$ and node $j$.
    \item $t_{ij}$: Travel time between node $i$ and node $j$.
    \item $q_i$: Demand of customer $i$.
    \item $[e_i, l_i]$: Time window for node $i$.
    \item $s_i$: Service time required at customer $i$.
    \item $C_k$: Maximum cargo capacity of vehicle $k$.
    \item $Q_k$: Maximum battery capacity of vehicle $k$.
    \item $h$: Energy consumption rate.
    \item $g_j$: Charging rate at station $j$.
\end{itemize}

\subsection{Decision Variables}
\begin{itemize}
    \item $x_{ijk}$: Binary, 1 if vehicle $k$ travels from $i$ to $j$.
    \item $A_{ik}$: Arrival time of vehicle $k$ at node $i$.
    \item $L_{ik}$: Remaining cargo load of vehicle $k$ at node $i$.
    \item $B_{ik}$: Remaining battery level of vehicle $k$ at node $i$.
    \item $c_{jk}$: Amount of energy charged to vehicle $k$ at station $j$.
    \item $u_k$: Binary, 1 if vehicle $k$ is used.
\end{itemize}

\subsection{Objective Function}
Minimize $(Z_1, Z_2, Z_3, Z_4)$ where:
\begin{align}
    Z_1 &= \sum_{k \in K} u_k \\
    Z_2 &= \sum_{i,j,k} d_{ij} \cdot x_{ijk} \\
    Z_3 &= \text{GiniCoefficient}(\{\text{ActiveTime}_k \mid k \in K, u_k=1\}) \\
    Z_4 &= \max_{k \in K} (\text{CompletionTime}_k)
\end{align}

\subsection{Constraints}
\textit{(Standard VRP, TW, Capacity, and Energy constraints apply.)}

\section{Solution Methodology: Adaptive Large Neighborhood Search (ALNS)}

The problem is solved using a sophisticated ALNS metaheuristic tailored for hierarchical multi-objective optimization.

\subsection{Overall Framework}

The ALNS algorithm starts with an initial solution and iteratively tries to improve it. In each iteration, a portion of the current solution is "destroyed" and then "repaired". The choice of destroy and repair methods is guided by an adaptive weight adjustment mechanism that rewards operators for finding high-quality solutions.

\begin{algorithm}[H]
\caption{ALNS Main Loop}
\begin{algorithmic}[1]
\Require Instance, ALNSConfig config
\Ensure ParetoArchive (set of non-dominated solutions)

\State $s_{\text{current}} \gets \text{generateInitialSolution()}$
\State $\text{archive.tryAdd}(s_{\text{current}})$
\State $currentTemperature \gets \text{config.startTemperature}$
\State $iterationsWithoutImprovement \gets 0$
\State $perturbationBoost \gets 1.0$
\State
\Comment{HV-based convergence state}
\State $previousHV \gets 0.0$
\State $hvStagnationCount \gets 0$
\State $lastMinVehicles \gets s_{\text{current}}.\text{getTotalVehicles()}$
\State
\For{iteration = 1 to config.maxIterations}
    \State $s_{\text{new}} \gets s_{\text{current}}.\text{copy()}$ \Comment{Uses SolutionPool for efficiency}
    \State
    \Comment{1. Destroy Phase}
    \State $n_{\text{to_remove}} \gets \text{calculateNodesToRemove(perturbationBoost)}$
    \State $destroy_{\text{op}} \gets \text{destroyPool.select(rng)}$
    \State $unserved_{\text{custs}} \gets destroy_{\text{op}}.\text{execute}(s_{\text{new}}, n_{\text{to_remove}}, \text{rng})$
    \State
    \Comment{2. Repair Phase}
    \State $repair_{\text{op}} \gets \text{repairPool.select(rng)}$
    \State $repair_{\text{op}}.\text{execute}(s_{\text{new}}, unserved_{\text{custs}}, \text{rng})$
    \State
    \State $s_{\text{new}}.\text{evaluateRoutes()}$ \Comment{Re-evaluate feasibility and all objectives}
    \State
    \If{$s_{\text{new}}$ is not feasible}
        \State Assign score for failure and continue
    \EndIf
    \State
    \Comment{3. Local Search Phase (Intensification)}
    \If{config.useLocalSearch and random() < config.localSearchIntensity}
        \State $\text{localSearch.run}(s_{\text{new}})$ \Comment{Apply 3-phase local search}
    \EndIf
    \State
    \Comment{4. Acceptance Criterion}
    \State $improved \gets \text{false}$
    \If{$s_{\text{new}}.\text{dominates}(s_{\text{current}})$}
        \State $s_{\text{current}} \gets s_{\text{new}}$
        \State Assign score for finding a new best solution
        \State $improved \gets \text{true}$
    \Else
        \State $add_{\text{res}} \gets \text{archive.tryAdd}(s_{\text{new}})$ \Comment{Add to Pareto archive}
        \If{$add_{\text{res}}$ is DOMINATING or NON_DOMINATED}
            \State $s_{\text{current}} \gets s_{\text{new}}$ \Comment{Move search to new Pareto-optimal region}
            \State Assign score for improving the archive
            \State $improved \gets \text{true}$
        \Else \Comment{$s_{\text{new}}$ is dominated, use Simulated Annealing}
            \State $\text{delta} \gets \text{calculateWeightedObjectiveDifference}(s_{\text{new}}, s_{\text{current}})$
            \If{$\exp(-\text{delta} / \text{currentTemperature}) > \text{random()}$}
                \State $s_{\text{current}} \gets s_{\text{new}}$
                \State Assign score for accepted dominated solution
            \Else
                \State Assign score for rejected solution
            \EndIf
        \EndIf
    \EndIf
    \State
    \Comment{5. Stagnation & Perturbation}
    \If{$improved$}
        \State $iterationsWithoutImprovement \gets 0$
    \Else
        \State $iterationsWithoutImprovement \gets iterationsWithoutImprovement + 1$
    \EndIf
    \If{$iterationsWithoutImprovement > 2000$}
        \State $perturbationBoost \gets 1.5$ \Comment{Increase destroy intensity}
    \ElsIf{$iterationsWithoutImprovement > 1000$}
        \State $perturbationBoost \gets 1.25$
        \State $currentTemperature \gets \text{config.startTemperature} * 0.8$ \Comment{Reheating}
        \If{$\text{random()} < 0.2$}
            \State $s_{\text{current}} \gets \text{archive.getRandomSolution(rng)}$ \Comment{Jump}
        \EndIf
    \Else
        \State $perturbationBoost \gets 1.0$
    \EndIf
    \State
    \Comment{6. Update Temperature}
    \State $currentTemperature \gets currentTemperature \times \text{config.coolingRate}$
    \State
    \Comment{7. Update Operator Weights & Check Hypervolume Convergence}
    \If{iteration \% config.segmentIterations == 0}
        \State $\text{destroyPool.updateWeights(config.decayParameter)}$
        \State $\text{repairPool.updateWeights(config.decayParameter)}$
        \If{$\text{checkHypervolumeConvergence}(\text{archive}, \text{lastMinVehicles}, \text{hvStagnationCount}, \text{previousHV})$}
            \State Break loop \Comment{Converged}
        \EndIf
    \EndIf
\EndFor
\State
\Comment{8. Optional: Scatter Search Intensification}
\If{config.useScatterSearch}
    \State $\text{scatterSearch.run}(\text{archive}, *this)$
\EndIf
\State
\State \Return $\text{archive.getFront()}$
\end{algorithmic}
\end{algorithm}

\subsection{Initial Solution}
A high-quality initial solution is generated using a problem-specific constructive heuristic. The heuristic adapts its strategy based on the instance type to improve the quality of the starting point.
\begin{itemize}
    \item \textbf{For R and RC instances (randomly distributed customers):} Customers are sorted by the tightness of their time windows (due date - ready time). This prioritizes customers with less scheduling flexibility.
    \item \textbf{For C instances (clustered customers):} A Clarke-Wright Savings-based approach is used to pre-sort customers, naturally grouping geographically close customers.
\end{itemize}
The heuristic then greedily inserts customers from the sorted list into routes, performing look-ahead checks for feasibility. A fallback mechanism creates individual routes (with station assistance if needed) for any remaining unserved customers.

\begin{algorithm}[H]
\caption{Initial Solution Generation}
\begin{algorithmic}[1]
\Require Problem Instance
\Ensure Initial Solution (Solution object)

\State $sol \gets \text{new Solution(instance)}$
\State $unservedCustomers \gets \text{list of all customers}$
\State
\Comment{1. Smart Sorting of Unserved Customers}
\If{instanceType is 'R' or 'RC'}
    \State Sort $unservedCustomers$ by Time Window Width (tightest first)
\Else \Comment{instanceType is 'C'}
    \State Sort $unservedCustomers$ using Clarke-Wright Savings logic
\EndIf
\State
\Comment{2. Main Construction Loop (Greedy Insertion)}
\While{$unservedCustomers$ is not empty and not cannotServeMore}
    \State Create new Vehicle and new Route ($currentRoute$)
    \While{not routeFinished}
        \State $bestCustId \gets -1$
        \State $bestScore \gets \infty$
        \ForEach{$custId$ in $unservedCustomers$}
            \State \Comment{Check feasibility (capacity, battery, time window)}
            \If{not feasible} \textbf{continue} \EndIf
            \State \Comment{Look-ahead check: Ensure return to depot or reachable station}
            \If{not canReturnToDepotOrStation(...)} \textbf{continue} \EndIf
            \State \Comment{Calculate score (e.g., 70\% distance, 30\% urgency)}
            \State $score \gets \text{calculateInsertionScore(...)}$
            \If{$score < bestScore$}
                \State $bestScore \gets score$
                \State $bestCustId \gets custId$
            \EndIf
        \EndFor
        \If{$bestCustId \neq -1$}
            \State Add $bestCustId$ to $currentRoute$ and update state
            \State Remove $bestCustId$ from $unservedCustomers$
        \Else \Comment{No customer can be served}
            \If{canChargeAtNearestStation(...)}
                \State Add nearest station to $currentRoute$ and update state
            \Else
                \State $routeFinished \gets \text{true}$
            \EndIf
        \EndIf
    \EndWhile
    \If{route is valid}
        \State $sol.\text{addRoute}(currentRoute)$
    \Else \Comment{Rollback if route became infeasible}
        \State Return customers to $unservedCustomers$ list
    \EndIf
\EndWhile
\State
\Comment{3. Fallback for remaining unserved customers (individual routes)}
\If{$unservedCustomers$ is not empty}
    \ForEach{$custId$ in $unservedCustomers$}
        \State Try to create a single route (D -> C -> D)
        \If{not feasible}
            \State Try with station assistance (D -> S -> C -> D)
        \EndIf
    \EndFor
\EndIf
\State
\State $sol.\text{evaluateRoutes()}$
\State \Return $sol$
\end{algorithmic}
\end{algorithm}

\subsection{Neighborhood Operators}
A rich set of destroy and repair operators are implemented to ensure a diverse search.

\subsubsection{Destroy Operators}
\begin{itemize}
    \item \textbf{UnifiedCostDestroy:} Removes customers based on a unified cost metric (distance, time, energy, or workload balance).
    \item \textbf{ShawDestroy (Relatedness):} Removes customers that are "related" (proximity, time window similarity, demand difference) to a seed customer.
    \item \textbf{InefficientRouteRemoval:} Removes all customers from an entire route deemed inefficient (few customers, high wait time, etc.).
    \item \textbf{RouteMergingDestroy:} Selects two geographically close routes and removes all their customers to encourage merging.
    \item \textbf{TargetedStationRemoval:} Removes inefficient charging stations to force the repair phase to find a better charging strategy.
\end{itemize}

\subsubsection{Repair Operators}
\begin{itemize}
    \item \textbf{Regret-K Repair:} Prioritizes inserting "hard-to-place" customers (those with the largest difference between their best and second-best insertion costs).
    \item \textbf{AdaptiveInsertion:} A greedy operator that randomly focuses on minimizing distance, balancing workload, or minimizing makespan.
    \item \textbf{GreedyEnergyInsertion:} A greedy operator that prioritizes insertions based on an energy-focused cost function.
    \item \textbf{ParetoFocusRepair:} Similar to \texttt{AdaptiveInsertion}, but strictly focuses on one objective to explore the extremes of the Pareto front.
    \item \textbf{SmartStationRepair:} Intelligently searches for the best station to add to a route to enable an otherwise infeasible customer insertion.
    \item \textbf{SmartTimeAwareStationRepair:} An advanced version using O(1) delta calculations and KNN station searches to find the best station insertion, including "Free Charge" opportunities.
\end{itemize}

\subsection{Adaptive Weight Adjustment}
The algorithm dynamically adjusts the selection probability (weights) of each operator. After a segment of iterations, the weights are updated based on the scores operators received. Operators that produce better solutions are rewarded with higher scores, increasing their chance of being selected in the future.

\subsection{Acceptance Criterion & Multi-Objective Handling}
A new solution $s_{\text{new}}$ is compared to the current solution $s_{\text{current}}$ using a multi-layered approach:
\begin{enumerate}
    \item \textbf{Dominance:} If $s_{\text{new}}$ dominates $s_{\text{current}}$ according to the hierarchical objectives, $s_{\text{current}}$ is replaced by $s_{\text{new}}$.
    \item \textbf{Pareto Archive:} The \texttt{ParetoArchive} stores all non-dominated solutions found so far.
    \begin{itemize}
        \item \textbf{Bucketing:} Solutions are stored in "buckets" based on their vehicle count.
        \item \textbf{Hierarchical Pruning:} When a new solution with $V$ vehicles is added, the archive \textbf{instantly and permanently deletes all buckets containing solutions with more than $V$ vehicles}. This strictly enforces the primary objective.
        \item \textbf{Crowding Distance:} If a bucket exceeds its maximum size, it is pruned by removing the solution in the most "crowded" region of the objective space (based on NSGA-II's crowding distance metric).
    \end{itemize}
    \item \textbf{Simulated Annealing (SA):} If $s_{\text{new}}$ is dominated by $s_{\text{current}}$, it can still be accepted based on a probability $\exp(-\text{delta} / T)$, where $\text{delta}$ is the degradation in a weighted-sum of the objectives and $T$ is the current "temperature". This allows the algorithm to escape local optima.
\end{enumerate}

\subsubsection{Early Stopping (Hypervolume Convergence)}
To avoid unnecessary iterations, the ALNS uses a \textbf{Hypervolume-based early stopping mechanism}:
\begin{itemize}
    \item At the end of each segment, the 3D Hypervolume of the current Pareto Archive is calculated (using Distance, Gini, and MaxTime for the lowest vehicle count found).
    \item If the relative improvement in Hypervolume falls below a threshold (\texttt{hvImprovementThreshold}) for a consecutive number of segments (\texttt{hvStagnationLimit}), the algorithm assumes the Pareto Front has converged and terminates early.
\end{itemize}

\subsection{Local Search Module (Updated)}
The ALNS integrates a powerful, three-phase local search module to intensify the search. It employs a "First Improvement" strategy, applying the first improving move found to accelerate the search process.

\subsubsection{Key Performance Optimizations}
\begin{itemize}
    \item \textbf{Tiered Filtering:} A multi-level check system to quickly prune unpromising moves before performing expensive, full evaluations.
    \begin{itemize}
        \item \textbf{Tier 3 (Bounding Check):} \texttt{Route::canPossiblyInsert} provides a fast, O(1) check on fundamental constraints (capacity, initial energy, time window start). It's used as a primary filter in \texttt{searchRelocate} and \texttt{searchSwap}.
        \item \textbf{Tier 2 (Delta Evaluation):} \texttt{evaluateRelocateDelta} calculates the change in distance for a move without copying the entire route object. It acts as a cheap, secondary filter.
        \item \textbf{Tier 1 (Full Evaluation):} \texttt{evaluateMove} performs a complete, but costly, evaluation by simulating the move on copied routes. This is only called if cheaper filters pass.
    \end{itemize}
    \item \textbf{Granular & KNN-based Neighborhoods:} The search space for inter-route moves is drastically reduced.
    \begin{itemize}
        \item \textbf{Granular Neighborhoods:} The \texttt{SearchContext} caches route centroids. Inter-route operators (like \texttt{Swap}, \texttt{Relocate}) only consider pairs of routes that are geographically close, based on a pre-calculated \texttt{distanceThreshold}.
        \item \textbf{K-Nearest Neighbors (KNN) Cache:} The $k$ nearest neighbors for each customer are pre-calculated. \texttt{searchRelocate} and \texttt{searchSwap} use this cache to focus only on the most promising insertion positions or swap candidates, avoiding a full scan.
    \end{itemize}
    \item \textbf{Static Move Descriptor (SMD):} A single \texttt{MoveDescriptor} object (\texttt{activeMove}) is reused across all search operations within the \texttt{LocalSearch} class to avoid repeated memory allocations and deallocations in the tight inner loops.
    \item \textbf{Adaptive Neighborhood Sizing:} The size of the neighborhoods explored by operators (e.g., \texttt{maxNodesToCheck_}, \texttt{maxSwapAttempts_}) is dynamically adjusted. It shrinks on success to intensify the search and expands on failure to diversify.
\end{itemize}

\subsubsection{Local Search Phases & Operators}
The local search is structured into three distinct phases, executed in a loop.
\begin{enumerate}
    \item \textbf{Phase 1: Distance Optimization (VND):} A Variable Neighborhood Descent that cycles through operators, restarting from the beginning whenever an improvement is found.
    \begin{itemize}
        \item \textbf{Relocate (1-Opt):} Moves a single customer to another position (intra- or inter-route).
        \begin{algorithm}[H]
        \caption{searchRelocate(solution, context)}
        \begin{algorithmic}[1]
        \ForEach{route r1 in solution}
            \ForEach{customer node_i in r1 (ranked by removal savings)}
                \State \Comment{Granular Filter (Route-level)}
                \ForEach{route r2 in context.neighborLists[r1]}
                    \State \Comment{KNN Filter (Node-level)}
                    \ForEach{candidate position j in findBestInsertionPositions_KNN(r2, node_i)}
                        \State \Comment{Tier 3 Filter}
                        \If{not r2.canPossiblyInsert(node_i, j)} \textbf{continue} \EndIf
                        \State \Comment{Tier 2 Filter}
                        \State delta = evaluateRelocateDelta(node_i, j)
                        \If{delta >= 0} \textbf{continue} \EndIf
                        \State \Comment{Tier 1: Full Evaluation}
                        \State evaluateMove(RELOCATE, node_i, j)
                        \If{move is feasible and improves objective}
                            \State applyMove(...) \Comment{First Improvement}
                            \State \Return true
                        \ElsIf{move failed due to energy}
                            \If{tryRelocateWithEnergyBoost(...)} \Comment{Specialized Heuristic}
                                \State \Return true
                            \EndIf
                        \EndIf
                    \EndFor
                \EndFor
            \EndFor
        \EndForEach
        \end{algorithmic}
        \end{algorithm}
        \item \textbf{Swap:} Exchanges the positions of two customers (intra- or inter-route). The search is similarly optimized with Granular, KNN, and Tiered filters.
        \item \textbf{2-Opt (Intra-route):} Reverses a segment within a single route to untangle paths. A quick distance-saving check is performed before the full evaluation.
        \item \textbf{Inter-2-Opt (Cross-route):} Exchanges the tails of two different routes. This powerful operator can significantly restructure the solution. It is filtered by route granularity.
        \item \textbf{Or-Opt:} Moves a contiguous segment of 2-3 customers to another position.
    \end{itemize}
    \item \textbf{Phase 2: Charging Optimization:} A set of operators run periodically to improve energy efficiency.
    \begin{itemize}
        \item \texttt{removeRedundantStations}: Removes stations that are unnecessary (e.g., provide negligible charge, or a bypass is feasible).
        \item \texttt{repositionStations}: Tries to move a station to a better location by swapping it with a closer alternative from the instance's station list.
        \item \texttt{searchStationSwap}: Replaces a station with a more "centroid-optimal" one, which is closer to the customer center-of-mass of the route.
        \item \texttt{optimizeChargingAmounts}: This logic is embedded within the \texttt{Route::evaluate} function, which automatically calculates the minimum required charge at each station. The operator focuses on removing stations that become redundant after this optimization (e.g., zero charge).
    \end{itemize}
    \item \textbf{Phase 3: Vehicle Reduction:} Aggressive operators run periodically or when the search stagnates to reduce the fleet size.
    \begin{itemize}
        \item \texttt{runSmartMultiRouteMerge}: Attempts to merge two small, nearby routes into one, or at least into two more efficient routes.
        \item \texttt{tryEliminateSmallestRoute}: Attempts to remove the route with the fewest customers by re-inserting all its customers into other routes in the solution.
    \end{itemize}
\end{enumerate}

\subsubsection{Specialized Heuristics}
\begin{itemize}
    \item \textbf{Energy Boost Relocate:} If a \texttt{Relocate} move is highly beneficial for distance but fails the final evaluation due to an energy deficit, this helper function attempts to salvage the move by intelligently inserting a charging station into the target route to restore feasibility.
\end{itemize}

\subsection{Perturbation}
To escape deep local optima during periods of stagnation, several perturbation mechanisms are used:
\begin{itemize}
    \item \textbf{Reheating:} The Simulated Annealing temperature is increased.
    \item \textbf{Archive Jump:} The current solution is replaced with a random solution from the Pareto archive.
    \item \textbf{Increased Destruction:} The number of customers to remove is temporarily increased.
\end{itemize}

\subsection{Scatter Search (Optional Intensification)}
The framework includes an optional \texttt{ScatterSearch} module that can be run after the main ALNS loop for further intensification.
\begin{itemize}
    \item \textbf{Reference Set:} It builds a reference set of high-quality (Tier 1) and diverse (Tier 2, based on crowding distance) solutions from the final Pareto Archive.
    \item \textbf{Combination Method:} It uses \textbf{Path Relinking} to generate new solutions by gradually transforming one parent solution into another, exploring the path between them.
    \item \textbf{Improvement:} New solutions generated via Path Relinking are improved using a short run of the ALNS algorithm before being submitted to the Pareto Archive.
\end{itemize}
